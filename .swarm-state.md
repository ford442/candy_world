## Iteration 0 — C++ vs TS ownership decision

Read `emscripten/physics.cpp` (`updatePhysicsCPP`, the native path used
off-lake) in full. Findings:

- Single-point `getGroundHeight(nextX, nextZ)` ground query — no footprint
  sampling, no normal/slope query at all.
- Hardcoded `nextY < groundY + 1.8f` eye-height snap — no configurable
  stepHeight, no ledge/step resolve (a taller obstacle just isn't detected;
  the player either lands on it if already at that Y or falls through the
  gap in the height check).
- One flat `smooth = 15.0f * delta` for horizontal velocity regardless of
  airborne/grounded state — no ground/air acceleration split.
- Jump fires only when `onGround == 1` in the same frame the input arrives
  (`if (onGround == 1 && jump) player.vy = 10.0f;`) — no coyote time, no
  jump buffering, no skinWidth hysteresis of any kind.

**Conclusion: the C++ path has none of the seven target behaviours.**

Per the task's own decision tree this would normally mean "build one
controller in TS that owns the kinematic resolve for both paths, with C++
supplying raw integration only." That is not achievable in this run: the
hard file boundary lists only specific `src/systems/physics/*.ts` files,
config fields, docs and tests as touchable. `emscripten/**` (and the
prebuilt `.wasm`/`build:emcc` output it produces) is not on that list, and
rebuilding/re-architecting the WASM boundary (e.g. having C++ return raw
velocity only, or exposing footprint/normal queries to it) is out of scope
for this slice.

**Decision (conservative option, arrived at from evidence, not a guess):**
The new TypeScript character controller owns the kinematic resolve for the
**JS-fallback path only** — `updateJSFallbackMovement`, used in the Melody
Lake basin and whenever `updatePhysicsCPP` returns `onGround < 0`. The
`updatePhysicsCPP` C++ path (off-lake) is left **byte-identical**: same
single-point ground snap, same flat acceleration, same immediate-only jump,
no slope/step/coyote/buffer there. This is stated explicitly as a
limitation in `docs/CHARACTER_CONTROLLER.md`.

Follow-up (not this run): extending `emscripten/physics.cpp` to call the
existing `ground.cpp` unified height query with a footprint/normal
equivalent, and to expose coyote/buffer timers, would need its own issue —
that touches `emscripten/**`, `verification/verify_emcc_exports.js`, and a
`build:emcc` rebuild, none of which are in this slice's file boundary.

## What was actually built this run

- `src/systems/physics/character-controller.ts` (NEW): pure function
  `resolveCharacterMovement(delta, player, targetVelocityXZ, jumpHeld,
jumpTriggered, groundQuery)`. Deliberately takes ground-sampling functions
  as an injected `groundQuery` parameter rather than statically importing
  `ground-system.ts` — that module transitively imports `wasm-loader.ts`,
  which does a Vite-only `import ... from '../wasm/candy_physics.wasm?init'`.
  Confirmed by direct experiment: `npx tsx -e "import('./src/systems/ground-system.ts')..."`
  fails outside Vite (`Cannot find package 'env'` after the wasm file
  exists, `?init` query fails before that). Existing tests in this repo
  (`tests/player-spawn.test.mjs`, `tests/ground-system.test.mjs`) route
  around this same problem by re-implementing pure logic instead of
  importing `ground-system.ts` directly. The injected-dependency design
  lets `tests/character-controller.test.mjs` import the _real_ production
  function under `tsx` while passing mock ground-query functions, and lets
  `physics-updates.ts` (which already runs inside the Vite bundle) pass the
  real `sampleGroundFootprint` / `getGroundHeight` at the real call site.
- `CONFIG.player` (types.ts + ground.ts `PLAYER_DEFAULTS`) gained: `radius`,
  `groundAccel`, `airAccel`, `jumpVelocity`, `stepHeight`, `skinWidth`,
  `coyoteTimeMs`, `jumpBufferMs`, `slopeLimit`. `slopeLimit` is a **new,
  player-owned** constant — does NOT reuse `CONFIG.ground.maxSlopeAngle`
  (the #1302 prop-placement constant; its doc comment in types.ts says
  exactly that, and coupling player movement to tree placement would be a
  real bug).
- `PlayerExtended` (physics-types.ts) gained `controllerClock`,
  `lastGroundedTime`, `jumpPressedTime` — an accumulated-delta clock, not
  wall-clock `Date.now()`/`performance.now()`, so coyote/buffer stay correct
  under frame stalls and the game's own time scaling.
- `updateJSFallbackMovement` (physics-updates.ts) rewritten to compute
  camera-relative target velocity (unchanged) then delegate the entire
  kinematic resolve to `resolveCharacterMovement`, passing the real
  `sampleGroundFootprint`/`getGroundHeight`. Preserved: the
  `spawnProtectFrames` gravity-freeze + last-frame re-snap from #1684 (moved
  inside the controller, same logic/thresholds), the
  `reconcileGroundedEyeY` pass from #1265 (kept in `physics-updates.ts`,
  runs after the controller, now gated on the _post-jump_ `isGrounded` so it
  no longer smooths Y on the same frame a jump fires — see "Known minor
  behaviour change" below), and the landing impact/audio/camera-shake
  block (including its pre-existing `fallSpeed` quirk — see below).
- Ability velocity hooks (`physics-abilities.ts`, `handleAbilities`) are
  untouched and still run before `updateJSFallbackMovement` is reached
  (physics-core.ts call order unchanged) — their velocity output remains an
  input to the controller, not something it redesigns.

### Known pre-existing quirk, preserved on purpose

`updateJSFallbackMovement`'s landing-FX branch has always computed
`fallSpeed = Math.abs(player.velocity.y)` **after** already zeroing
`velocity.y` on the ground-snap path, so `fallSpeed` was always `0` and the
"soft landing" FX branch always fired regardless of actual fall speed. This
is not one of the seven behaviours #1577 asks for, so it was left exactly
as-is (same ordering, same bug) rather than fixed as a drive-by change. Not
touched, not silently changed either — documented in the doc rewrite too.

### Known minor behaviour change (accepted, justified above)

Previously `reconcileGroundedEyeY` ran unconditionally on `isGrounded`
computed _before_ the jump check, then the jump check could still fire and
overwrite `velocity.y`/`isGrounded` afterward — net velocity/isGrounded
result was identical either order (jump always wins), but the reconcile
lerp could nudge `position.y` toward the ground target on the very same
frame a jump also fired. Now that jump resolution lives inside
`resolveCharacterMovement` (before the outer reconcile check),
`isGrounded` is already `false` by the time `physics-updates.ts` decides
whether to reconcile, so the reconcile lerp is skipped on a jump frame.
Considered acceptable: it doesn't change jump velocity or any of the FX
paths, and arguably fixes a latent smoothing artifact rather than
introducing one.

## Test-can-fail proof

Done. With the real test file in place, temporarily edited
`character-controller.ts`'s step-height check from `if (rise > stepHeight)`
to `if (rise > stepHeight * 1000)` (i.e. broke the ledge-block behaviour
without touching any config default). Re-ran `npm run test:character`:
`# pass 9 / # fail 1`, with `not ok 5 - ledge over CONFIG.player.stepHeight
blocks forward motion` failing as expected. Reverted the line back to
`if (rise > stepHeight)`, re-ran: `# pass 10 / # fail 0`. Confirms the test
suite exercises real production logic, not a tautology.
(Earlier attempt: first tried shrinking `PLAYER_DEFAULTS.stepHeight` from
`0.35` to `0.05` — this did NOT fail, because the step tests compute their
rise thresholds relative to `CONFIG.player.stepHeight` rather than a
hardcoded absolute value, so they scale with the constant. That's correct
test design (no duplicated magic numbers) but not useful as a fail-proof
demonstration, which is why the code-level break above was used instead.
Recorded so a future run doesn't retry the same non-signal.)
