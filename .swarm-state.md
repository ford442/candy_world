## Iteration 0 — C++ vs TS ownership decision

Read `emscripten/physics.cpp` (`updatePhysicsCPP`, the native path used
off-lake) in full. Findings:

- Single-point `getGroundHeight(nextX, nextZ)` ground query — no footprint
  sampling, no normal/slope query at all.
- Hardcoded `nextY < groundY + 1.8f` eye-height snap — no configurable
  stepHeight, no ledge/step resolve (a taller obstacle just isn't detected;
  the player either lands on it if already at that Y or falls through the
  gap in the height check).
- One flat `smooth = 15.0f * delta` for horizontal velocity regardless of
  airborne/grounded state — no ground/air acceleration split.
- Jump fires only when `onGround == 1` in the same frame the input arrives
  (`if (onGround == 1 && jump) player.vy = 10.0f;`) — no coyote time, no
  jump buffering, no skinWidth hysteresis of any kind.

**Conclusion: the C++ path has none of the seven target behaviours.**

Per the task's own decision tree this would normally mean "build one
controller in TS that owns the kinematic resolve for both paths, with C++
supplying raw integration only." That is not achievable in this run: the
hard file boundary lists only specific `src/systems/physics/*.ts` files,
config fields, docs and tests as touchable. `emscripten/**` (and the
prebuilt `.wasm`/`build:emcc` output it produces) is not on that list, and
rebuilding/re-architecting the WASM boundary (e.g. having C++ return raw
velocity only, or exposing footprint/normal queries to it) is out of scope
for this slice.

**Decision (conservative option, arrived at from evidence, not a guess):**
The new TypeScript character controller owns the kinematic resolve for the
**JS-fallback path only** — `updateJSFallbackMovement`, used in the Melody
Lake basin and whenever `updatePhysicsCPP` returns `onGround < 0`. The
`updatePhysicsCPP` C++ path (off-lake) is left **byte-identical**: same
single-point ground snap, same flat acceleration, same immediate-only jump,
no slope/step/coyote/buffer there. This is stated explicitly as a
limitation in `docs/CHARACTER_CONTROLLER.md`.

Follow-up (not this run): extending `emscripten/physics.cpp` to call the
existing `ground.cpp` unified height query with a footprint/normal
equivalent, and to expose coyote/buffer timers, would need its own issue —
that touches `emscripten/**`, `verification/verify_emcc_exports.js`, and a
`build:emcc` rebuild, none of which are in this slice's file boundary.

### Known pre-existing quirk, preserved on purpose

`updateJSFallbackMovement`'s landing-FX branch has always computed
`fallSpeed = Math.abs(player.velocity.y)` **after** already zeroing
`velocity.y` on the ground-snap path, so `fallSpeed` was always `0` and the
"soft landing" FX branch always fired regardless of actual fall speed. This
is not one of the seven behaviours #1577 asks for, so it was left exactly
as-is (same ordering, same bug) rather than fixed as a drive-by change. Not
touched, not silently changed either — documented in the doc rewrite too.

### Known minor behaviour change (accepted, justified above)

Previously `reconcileGroundedEyeY` ran unconditionally on `isGrounded`
computed _before_ the jump check, then the jump check could still fire and
overwrite `velocity.y`/`isGrounded` afterward — net velocity/isGrounded
result was identical either order (jump always wins), but the reconcile
lerp could nudge `position.y` toward the ground target on the very same
frame a jump also fired. Now that jump resolution lives inside
`resolveCharacterMovement` (before the outer reconcile check),
`isGrounded` is already `false` by the time `physics-updates.ts` decides
whether to reconcile, so the reconcile lerp is skipped on a jump frame.
Considered acceptable: it doesn't change jump velocity or any of the FX
paths, and arguably fixes a latent smoothing artifact rather than
introducing one.

## Post-review fixes (PR #1696, CodeRabbit)

After opening PR #1696, CodeRabbit's automated review flagged two real
issues, both verified and fixed:

1. **Confirmed bug — coyote eligibility not consumed on jump.** In
   `resolveCharacterMovement`'s jump-firing branch, `lastGroundedTime` was
   never reset when a jump fired via the coyote window. Since `canJump` is
   computed from `controllerClock - lastGroundedTime <= coyoteSec` and that
   check doesn't otherwise advance once the player leaves the ground, a
   held jump key (`jumpHeld` stays true) would keep re-entering the branch
   and resetting `velocity.y = jumpVelocity` every frame for the rest of the
   _original_ coyote window — a sustained-hover glitch instead of one
   impulse. Verified by hand-tracing the logic, then confirmed with a new
   regression test (`coyote time: a held jump does not refire on the next
airborne frame`) that fails without the fix and passes with it (checked
   both ways: removed the `player.lastGroundedTime = -Infinity;` line,
   watched `# fail 1`, restored it, watched `# pass 11`). Fix: set
   `player.lastGroundedTime = -Infinity` alongside the existing
   `jumpPressedTime` consumption in that branch.
2. **Doc accuracy — "pure function" was wrong.** `docs/CHARACTER_CONTROLLER.md`
   described `resolveCharacterMovement` as a pure function; it mutates the

## Root-cause note (why boot was actually slow)

Before this change, `generateMap()` for FULL mode did:

1. Phase 1: spawn up to 300 entities within 80m, synchronously (already
   present pre-PR).
2. Phase 2: queue the rest via `streamEntitiesNear` (non-blocking, already
   fine).
3. **`await populateProceduralExtras() / populateGemCanopyCorridor() /
populateMyceliumGrove() / populateCloudArchipelago() / populateSkyIslands()`
   — all awaited inline, blocking `generateMap()`'s promise.**

Since `start-screen.ts` does `await populateWorld(...)` before calling
`markReadinessPlayable()`, step 3 was the real critical-path blocker — not
just the `mapSizeWaitsForFullPopulation` UI flag (which only ever gated
loading-screen progress-bar cosmetics for `large` map size, after
`populateWorld()` had already resolved). Moving step 3 to
`queueDecoratorBootstrap()` (background-enqueued, not awaited) is what
actually removes the blocking wait on **both** boot paths.

## Bug found AND fixed during verification

**`RegionManager.getCellsToUnload()` (region-manager-lod.ts) was unsafe to
use as-is.** My first implementation of `ChunkStreamer.evictFarChunks()`
called `this.region.getCellsToUnload(cx, cz, evictRingChunks)` per the "reuse
the existing grid, don't fork it" instruction. Live-browser testing caught it
immediately: walking one single chunk over (well within the 4-ring/128m evict
radius) triggered **evicting all 25 currently-loaded chunks**, including the
spawn chunk itself.

Root cause (as far as I chased it — the file itself is out of scope for this
PR): `getCellsToUnload()` routes through `batchDistanceCull()` (WASM,
`assembly/batch.ts`), whose flag semantics are `1.0 = within range` / `0.0 =
far`, and the JS-side interpretation (`flags[i] === 0.0` → push to unload)
matches that correctly on paper — but in the live app the returned flags
don't discriminate by distance at all (every loaded cell comes back as a
candidate). `RegionManager` was **dormant** before this change (registered
nowhere in the live game loop — grepped `region-manager-core.ts` /
`region-manager.ts` usage pre-PR: only `asset-streaming-core.ts`, itself
unused by `main.ts`/game-loop). This PR is the first real caller of
`getCellsToUnload()`, so this looks like a latent, previously-unexercised bug
in `region-manager-lod.ts`, not something my diff introduced.

**Fix:** `evictFarChunks()` now does its own direct chunk-distance check in
`chunk-streamer.ts` (iterating `this.records`, not `RegionManager.cells`) and
only uses `RegionManager` for cell **state** bookkeeping (`getCell`,
`forceUnloadCell`) — not the buggy distance-cull helper. `getCellsToLoad()` is
still used for the load side; it's pure-JS spiral generation with no WASM
dependency and tested fine (background streaming grew correctly, spawn-tile
cap held). Re-verified after the fix: foliage count stayed flat (505 → 505)
across a boundary-crossing walk that shouldn't have evicted anything, vs.
losing 174 objects before the fix.

**Follow-up recommended (not done here, `region-manager-lod.ts` not in this
PR's allowed files):** root-cause `batchDistanceCull`'s flag output not
discriminating by distance in the live app — possibly a stale/detached
typed-array view over WASM memory after a `memory.grow()` elsewhere, since
`outputView` in `wasm-batch-core.ts` is allocated once and other systems
(foliage LOD culling, physics) also grow/use the same WASM instance. Anyone
calling `RegionManager.getCellsToUnload()` / `getDistantCells()` elsewhere in
the future should treat them as unverified until this is chased down.

## Design choices / eviction scope (the "known risk" the task flagged)

- **Discovery grid (`optimizedDiscovery`, WASM/AS spatial grid) has no
  unregister API** (checked `discovery-optimized.ts` — only `registerObject`
  and a full `reset()`). ChunkStreamer registers each newly-spawned object
  once (deduped by `obj.uuid`) and **never unregisters on eviction** — the
  discovery grid keeps a stale entry at that position/type after the mesh is
  despawned. Practically: if a player evicts a chunk (walks >128m away) and
  later walks back near the _exact_ old position before the mesh respawns,
  they could see a discovery toast for something not visually there yet. Cosmetic,
  not a crash. A real fix needs an `unregisterObject(id)` added to
  `discovery-optimized.ts` (not in this PR's allowed files).
- **Eviction is conservative on batched (InstancedMesh) entities.** Only
  `mushroom` type entities have a public removal API
  (`MushroomBatcher.removeInstance`). Every other batched type (flowers,
  arpeggio_fern, portamento_pine, gem_canopy_tree, glass_mushroom,
  prism_rose_bush — see `isKnownBatchedType()` in chunk-streamer.ts, mirrors
  `safeAddFoliage`'s local `isBatched` check since that logic isn't exported)
  and `cave` (WASM collision + weatherSystem registration, no removal) are
  classified `'never'` — loaded permanently once streamed in, never evicted.
  This trades a bounded amount of "world never fully unloads" memory for
  correctness (no corrupted/leaked InstancedMesh indices). Non-batched
  individual-mesh entities (most musical-flora types: panning_pad,
  instrument_shrine, silence_spirit, kick_drum_geyser, etc.) evict fully:
  removed from `foliageGroup` + every tracking array in `state.ts` +
  `vineSwings` (for `swingable_vine`), disposed via `safeRemoveAndDispose`,
  and the entity id is freed from `spawnedIds` so walking back respawns it.
- **`obstaclesData` (generation-utils.ts) is dead code** — verified via
  repo-wide grep: written by `safeAddFoliage` but read nowhere. Actual
  obstacle/collision consistency comes entirely from `populatePhysicsGrids()`
  (physics-core.ts), which rebuilds fully from `animatedFoliage` /
  `foliageTraps` / `foliageGeysers` / `foliagePortamentoPines` /
  `foliagePanningPads` every call — so as long as ChunkStreamer keeps those
  arrays in sync on evict (it does) and calls `populatePhysicsGrids()` after
  (it does, via a `physicsDirty` flag checked once per frame in `update()`),
  physics stays consistent. No separate WASM obstacle buffer to desync.

## Footguns for whoever picks this up

- `ChunkStreamer` is a per-boot singleton (`setActiveChunkStreamer`/
  `getActiveChunkStreamer` in chunk-streamer.ts). `generateMap()` calls
  `setActiveChunkStreamer(null)` at the top (disposes any previous instance)
  before branching on `bootPath` — important for world regeneration
  (`btn-map-*` → re-click Enter) not to leak the old streamer or double-drive
  `update()`.
- `loadSpawnPlayable()`'s 80-entity cap skips a chunk **whole** if it doesn't
  fit the remaining budget, rather than partially spawning it — this keeps
  chunk state binary (UNLOADED/LOADED, no partial state to track) at the cost
  of the boot batch sometimes being noticeably under 80 even when a couple
  more entities would technically fit. Acceptable given the target is "≤80",
  not "as close to 80 as possible."
- Background chunk-entity tasks are enqueued **one per entity**
  (`chunk_stream_${chunkKey}_${id}`), matching the existing `map_stream_*`
  convention from the explore path — not batched into one task per chunk.
  This keeps `globalBackgroundProcessor`'s per-task time-budgeting granular
  (a single slow tree spawn only overruns by itself, doesn't drag a whole
  chunk's worth of entities into one unbudgeted block).
